# Internationalization Strategy

## Purpose

MangAI must support internationalization from the beginning at two different levels:

- product internationalization: the app UI, messages, formatting, and accessibility of the product itself
- content localization: the source and target languages of the comic workflow

The current planning already covers content languages reasonably well. This document ensures the product architecture also supports multilingual UI and language-aware typesetting.

## Current Assessment

### Already Present

- project-level `source_language`
- project-level `target_language`
- translation pipeline
- language-aware content workflows

### Missing Or Weak Before This Document

- app UI locale strategy
- direction-aware typesetting contracts
- font fallback strategy by language and script
- API localization rules
- i18n responsibilities by layer
- i18n testing expectations

## Core Principles

- use BCP 47 language tags everywhere possible
- keep UI locale separate from project source and target languages
- never hardcode user-facing strings in product code
- backend contracts should prefer stable error codes over localized prose
- text layout must be language-aware, not only string-length-aware
- font choice must support script coverage, not just aesthetics

## Scope Split

## 1. Product UI Internationalization

This covers:

- interface language
- labels
- system messages
- empty states
- error messages
- date, time, and number formatting

Recommended initial UI locales:

- `en-US`
- `pt-BR`

These are the initial supported UI locales for the MVP.

Assumption for now:

- `Portuguese` means `pt-BR` in the first implementation

Future expansion may add:

- `pt-PT`
- additional regional English variants

## 2. Content Language Support

This covers:

- source page language
- translation target language
- OCR language hints
- text direction
- line-breaking behavior
- font fallback
- export compatibility

## MVP Focus Languages

For the first implementation cycle, MangAI should optimize its product and content defaults around:

- `en-US`
- `pt-BR`

This means:

- UI catalogs should exist for English and Portuguese
- formatting should be validated in both locales
- style presets and font fallback should be tested for English and Portuguese text
- initial typesetting assumptions may remain `ltr`

This does not prevent later support for other source languages in OCR or other target languages in translation, but the first product-quality pass should be strongest in English and Portuguese.

## Canonical Rules

### Language Tags

- store language values as BCP 47 strings such as `ja-JP`, `en-US`, `pt-BR`
- avoid loose two-letter values unless they come from external providers and are normalized before persistence

### UI Locale

- UI locale belongs to the user session or user preferences, not to the page content itself
- the same project may be edited by users with different UI locales in the future

### Text Direction

At minimum, MangAI should support:

- `ltr`
- `rtl`

Future-ready support should consider:

- `ttb` for vertical layout or writing-mode-aware placement

MVP note:

- for `en-US` and `pt-BR`, the active default is `ltr`
- `rtl` and `ttb` should remain contract-ready but not implementation-critical in the first release

### Message Strategy

- frontend owns localization of UI copy
- backend returns machine-stable `error_code` values
- backend may return a fallback English developer-readable message, but web should render localized user-facing copy

## Layer Responsibilities

### `packages/shared`

- locale enums where fixed values exist
- direction enums
- locale-aware DTOs
- schema validation for language and direction fields

### `apps/web`

- translation catalogs
- locale switcher
- localized UI rendering
- locale-aware formatting
- direction-aware text editing controls where needed

### `services/api`

- validate locale and language tags
- persist canonical language values
- return stable error codes
- avoid embedding presentation-specific translations

### `services/workers`

- consume normalized language and direction fields
- respect OCR and translation language hints
- emit outputs that preserve language metadata

## MVP I18N Scope

The MVP should include:

- multilingual-ready app architecture
- UI support for `en-US` and `pt-BR`
- BCP 47 language tags in schema and contracts
- locale-aware UI formatting
- target text direction in typesetting contracts
- language-aware font preset and fallback planning

The MVP does not need:

- dozens of UI locales
- full glossary localization
- advanced bidirectional text editing
- full vertical Japanese typesetting automation

## Typesetting Implications

Internationalization affects typesetting directly.

The typesetting system must eventually support:

- language-aware line breaking
- direction-aware alignment defaults
- language-specific font fallbacks
- per-language style presets
- export-safe font substitution rules

## Export Implications

- exported PSD and JPG must preserve the intended language and font choices as much as possible
- missing-font scenarios must be predictable and diagnosable
- PSD export should record the chosen font family and fallback chain when possible

## Quality Requirements

- all user-facing UI text must come from message catalogs
- all persisted language values must be normalized before storage
- all core flows must be testable in more than one UI locale
- typesetting heuristics must be tested against at least LTR and future RTL scenarios

## Recommended Technical Direction

### Frontend

- use a dedicated i18n layer from the first web bootstrap
- organize messages by feature area, not one huge flat file

### Backend

- use shared validators for BCP 47 normalization
- use stable `error_code` fields in error responses

### Shared

- define `TextDirection`
- define locale-aware DTOs
- centralize schema helpers for language validation

## Open Decisions

- whether `pt-BR` should later expand into a generic Portuguese strategy or remain a separate locale track
- how far MVP should go on RTL support
- exact font fallback strategy by language family
